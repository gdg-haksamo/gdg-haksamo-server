# 0002 — 크롤 신규 메뉴 정보(한줄설명·탄단지) Gemini 배치 생성

- 상태: **채택** (2026-06-25)
- 관련: 이슈 #62, erd-decisions #19, [[0001]]

## 배경
메뉴의 한줄설명(`description`)·탄단지(`calories`/`protein`/`carb`/`fat`)는 크롤로 못 얻어 Gemini로 생성한다(erd-decisions #19). 이미지는 별도(관리자 수동 주입, 데모 임시책). 비용을 줄이면서 데이터 정합성을 지키는 호출·저장 방식을 정한다.

## 결정
1. **신규 메뉴만 생성.** `description` 또는 영양값이 `NULL`인 Menu만 대상. 기존/재등장 메뉴는 스킵 → 비용이 *역대 고유 메뉴 수*에만 묶이고 사용자 수와 무관.
2. **한 번에(배치) 호출.** 대상 메뉴들을 모아 한 호출에 넣어 순서대로 결과를 받는다(메뉴당 1호출 대비 토큰·요청 수 절감).
3. **id echo 매칭(위치 의존 금지).** 각 메뉴에 `id`를 부여해 프롬프트에 넣고, 응답이 그 `id`를 그대로 돌려주게 한다. 저장은 **위치가 아니라 id로 매칭**한다.
4. **청크 분할.** 첫 크롤은 수백 개라 한 호출에 다 넣으면 응답이 잘린다 → 적정 크기(예: 20~30개)로 나눠 호출.
5. **원자적 저장.** 한 청크 응답에서 **요청한 id가 모두 매칭되는지 검증한 뒤** 그 청크를 저장. 누락/불일치면 그 청크는 저장하지 않고 로깅(부분 오염 방지).
6. **크롤 본체와 분리/비동기.** `MenuSchedule` 저장은 즉시 끝내고, 정보 생성은 뒤에서 채운다(첫 조회자가 빈 값 봐도 곧 채워짐).

## 근거 — 왜 id 매칭·청크인가
LLM에 50개 이상을 주고 "순서대로 돌려줘"라고 하면 **하나를 누락하거나 순서를 바꾸는 경우가 생긴다.** 위치로 저장하면 탄단지가 엉뚱한 메뉴에 들어가 **조용히 데이터가 오염**된다. id를 echo시켜 매칭하면 이 오류를 저장 전에 잡을 수 있다. 청크는 응답 토큰 한도(잘림) 회피용.

## 비용
- 출력 토큰이 비용의 대부분. 메뉴 1개당 설명+영양 ≈ 80~120 토큰.
- 고유 메뉴 ~800개 1회 생성 ≈ 출력 ~80K 토큰 ≈ **일회성 ~$0.03**.
- 이후 주당 신규 ~10개 ≈ 주당 수십 원. 사실상 무시 가능.

## 영향
- 크롤 저장(upsert) 직후, NULL 메뉴 수집 → 청크 호출 → id 검증 → 저장 파이프라인 추가.
- 추천 프롬프트가 이 탄단지를 입력으로 쓰므로([[0001]]) 값이 채워질수록 추천 품질도 향상.
